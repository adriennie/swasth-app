# Supabase Setup and Demo Data

## 1. What is in `supabase/`

| File | Contents |
| --- | --- |
| `migrations/20261025000000_init_schema.sql` | Tables, triggers, row-level security, and the `hercircle_assets` image bucket |
| `seed.sql` | Synthetic demo accounts, starter catalog, stock, and order history |
| `catalog.sql` | Extended catalog of 220 more products, generated by `scripts/generate-catalog.js` |
| `config.toml` | Supabase CLI settings for local development |

These replace the old root scripts (`CREATE_ORDERS_TABLES.sql`, `UPDATE_DB.sql`, `ADD_OTP_COLUMN.sql`, `SET_MOQ_VALUES.sql`).

## 2. Data model

| Table | Purpose |
| --- | --- |
| `admins` | Users with admin rights |
| `pharmacy_profiles`, `distributor_profiles` | Business accounts and approval status |
| `pharmacy_distributors` | Which distributors supply which pharmacies |
| `products` | Master catalog: `price` (pharmacy cost), `distributor_price`, `mrp`, `moq` |
| `pharmacy_inventory` | Pharmacy stock with reorder level, batch, and expiry |
| `distributor_stock` | Distributor stock, one row per product |
| `distributor_cart_items` | Distributor cart before ordering from admin |
| `orders`, `order_items` | Pharmacy → distributor orders (`distributor_id` null = admin queue) |
| `distributor_admin_orders`, `distributor_admin_order_items` | Distributor → admin purchase orders |

### Consistent business IDs

A profile's `id` is the business's auth user id. `user_id` is kept for existing queries and always equals `id`. Every `pharmacy_id` and `distributor_id` column therefore holds an auth user id.

### Server-enforced rules

- Row-level security limits every table to its owner, mapped partners, and admins.
- Admins are users listed in `admins`, checked by `is_admin()`.
- Signups always start as `pending`, and only admins can change a profile's `status`.
- Order statuses are stored in lowercase and limited to `pending`, `confirmed`, `processing`, `shipped`, `delivered`, `cancelled`, and `rejected`.
- Only admins can change the catalog or upload product images.

## 3. Run locally (recommended)

Requires Docker Desktop and the Supabase CLI.

```bash
brew install supabase/tap/supabase
```

```bash
supabase start
```

```bash
supabase db reset
```

`supabase start` prints the local API URL and anon key. Put them in `.env.local`:

```env
EXPO_PUBLIC_SUPABASE_URL=http://127.0.0.1:54321
EXPO_PUBLIC_SUPABASE_ANON_KEY=<anon key from supabase start>
```

For a hosted project, `EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY` also works. Never put the secret (service role) key in an `EXPO_PUBLIC_` variable or a committed file: it bypasses row-level security.

Run `supabase db reset` again at any time to restore the demo data. Studio runs at <http://127.0.0.1:54323>.

## 4. Use with a hosted project

The migration expects an empty `public` schema. Running it on the existing hosted project fails on tables that already exist, and the seed adds demo users to that project's auth. Use a new project for the demo:

1. Create a new Supabase project and put its URL, publishable key, and secret key in `.env` (`EXPO_PUBLIC_SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY`).
2. In the SQL editor, run the migration file.
3. Create the demo accounts. Hosted Supabase blocks SQL writes to auth tables, so this uses the Auth Admin API with the secret key:

   ```bash
   npm run seed:users
   ```

4. Load the demo data. Add the session pooler connection string to `.env.local` (dashboard → Connect → Session pooler, with your database password filled in):

   ```env
   SUPABASE_DB_URL=postgresql://postgres.<project-ref>:<password>@<pooler-host>:5432/postgres
   ```

   Then run:

   ```bash
   npm run seed:data
   ```

   Then load the extended catalog (safe to re-run):

   ```bash
   npm run seed:catalog
   ```

   `seed:data` runs `seed.sql` as one transaction and refuses to run if the project already has orders. Running `seed.sql` in the SQL editor works too. The session pooler is needed because the direct database address is IPv6-only.
5. Under Authentication → Providers → Email, turn off email confirmation. The signup screens insert the business profile right after `signUp`, which needs an active session.

`.env.local` holds a copy of the publishable key as `EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, the only form Expo bundles into the app. Write the value itself: SDK 58 does not reliably expand `${SUPABASE_PUBLISHABLE_KEY}` references across env files. The secret key is used only by `scripts/seed-demo-users.js`, which runs on your machine.

## 5. Demo data

All demo data is synthetic. Do not present forecasting or anomaly results on it as real-world accuracy.

| Data | Amount |
| --- | --- |
| Products | 250 general medicines, women's health products, first aid and devices across 17 categories (30 in `seed.sql`, 220 in `catalog.sql`) |
| Pharmacy inventory | About 60 rows, including low-stock items and batches expiring within 60 days |
| Distributor stock | Full catalog for both approved distributors |
| Pharmacy orders | About 115 over the last 90 days, mostly delivered; recent ones pending, confirmed, or shipped |
| Admin queue | 2 pending CarePlus orders with no distributor |
| Distributor purchase orders | 4 per approved distributor (Completed, Shipped, Pending) |
| Distributor cart | 3 items in MedLine's cart |

Orders are heavier on Mondays and Tuesdays so forecasts have a weekly pattern. The seed uses a fixed random seed, so every reset produces the same data.
